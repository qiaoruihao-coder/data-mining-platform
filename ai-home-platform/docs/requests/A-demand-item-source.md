# A：需求列表逐条来源标识

- 申请角色：A；状态：待 D 讨论，尚未修改公共契约。
- 用户场景：业主新建的数据库需求与 `demo-demand` 同时返回时，GET /api/demand 整体标 mock。前端无法仅凭信封判断每条来源，不能把所有记录称为模拟或自行猜测字段。
- 当前独立交付：列表使用公共 `Demand` 解析；mock 时提示可能混有模拟与实际保存记录，并让用户打开详情核实单条来源。保留整体来源，不按 ID 猜测单条真实性，也不批量请求详情。
- 请求 D 维护：`src/contracts/index.ts`、需求服务映射和 GET 列表/详情、固定数据与相关测试、`docs/API.md`；必要时由 D 决定数据库如何保存来源。
- 建议字段：在公共 `Demand` 中新增可选 `source?: 'mock' | 'live'`，无单位。过渡期可选以兼容已有调用方，列表与详情路由应始终填入服务端确定的来源。字段缺失表示未知；不能以缺失或 `simulated: false` 推断为 live。保留现有 `meta.source` 语义，不加入第二套 `simulated` 字段。
- 响应示例（其余 Demand 字段省略，最终仍需完整契约）：`{ok:true,data:[{id:'demo-demand',source:'mock',...},{id:'saved-demand',source:'live',...}],meta:{source:'mock'}}`。查询参数、金额与状态均不变；该字段不得成为创建或更新输入。
- 受影响模块：A 需求列表/详情，B 需求读取与匹配，C 需求大厅/详情，D 需求 API。新增输出字段应向后兼容；各角色在 D 合并后再接入，不直接改对方目录。
- 验收：混合列表分别返回 mock/live；演示详情为 mock、新建详情为 live；失败不回退 mock；旧记录或旧响应缺字段时客户端显示未确认；创建/更新拒绝客户端指定来源；整体信封保留既有标记规则。
