# B：接受报价后的实际接单只读核实

2026-11-14，基于 main `9451411`。#133 的排序数据请求已合入，但 Provider 仍无档期/履约汇总字段；本次先接入 D 已交付的 #132 业主接单读取，补齐 #121 接受流程的结果核实。

## 行为

- 保留明确确认后才 POST 的流程。提交结束后先刷新需求与报价，再通过公共 `OrderQuery`、`OwnerOrderResult` 调用 `GET /api/order?demandId=…`；200/201 回执、409/503/网络异常后的核实均不再次写入。
- 回读接单必须与最新报价快照中的唯一 accepted 报价、需求 ID/状态、服务方和逐条/整体来源一致；不同请求之间状态恰好发生变化时提示重新刷新，不拼接出假成功。
- 只读查得所选报价的实际关系才显示“所选报价已有实际接单关系”，附关系编号、报价/服务方编号、状态及来源；若实际关系选择了其他报价，显示不能改选。
- 合法 `data:null` 显示本次尚无实际关系；历史 accepted 不补造关系。已接单需求却返回 null、来源不一致、坏 DTO、401/403/404/501/503 均不能显示空成功。失败提示与报价列表分别保留。
- 每次报价刷新开始即隐藏旧关系编号；只使用对应本轮报价快照的结果。失效请求的迟到结果被忽略。用户点“刷新报价”继续只读核实，仍不解锁再次提交。
- 提交成功回执只提示曾收到成功响应；当前编号由只读查询展示，读取失败时不以提交回执编号兜底。固定 demo-demand 无接单查询，保持公开只读报价演示。
