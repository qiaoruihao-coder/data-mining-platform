## 场景与现状

业主希望在同城、施工工种符合的团队中，结合可用工期与历史履约表现选择候选。现有 B 算法是标签匹配 60 分、`Provider.rating × 8` 四舍五入最多 40 分，同分按 ID；`rating` 没有已完成接单的统计依据，不能改名为履约评分。

`GET /api/provider` 仍返回固定 mock。最新 main 已提供实际接单、履约推进与本人评价，见 `D-order-progress.md`、`D-review-create.md`，但明确没有公开评价或服务方评分聚合。不能由 B 遍历受保护的本人评价接口收集其他业主的数据。档期没有录入或可核实来源；某单的计划天数、报价预计天数、当前未接单，都不能证明团队未来有空。

## 请 D 决定的数据来源

1. **档期**：是否先提供明确标注的固定 mock 窗口用于演示？若接真实数据，谁维护团队可用窗口、如何核实并更新、是否存在多班组容量？在来源未建立时返回未知，不从现有接单/排期推算“保证可施工”。建议第一版只表达团队声明的连续可用日期窗口，不承担预约、锁定或产能承诺。
2. **履约评价**：建议从服务端核验过的 completed 需求及 ServiceOrder 关联评价聚合，一接单一评价，禁止用种子 `rating` 补齐。它表示“已完成接单的业主评价均分”，不是准时率、质量鉴定或已审核信用分。请确认是否接受该定义作为本轮履约排序指标。
3. **来源隔离与可见性**：建议真实统计只计 source=live 且关联来源一致的记录；mock 样本仅用于独立演示口径，不与 live 混算。真实无样本必须明确无样本，不能自动改用演示值。请 D 决定公开汇总的授权范围；仅输出汇总值与样本数，不输出评论、业主、需求或接单 ID。
4. **交付顺序**：可先冻结并交付评价汇总，再提供档期；B 分两个小功能接入。当前只有演示服务方认证，实际走通的 mock 接单及评价仍是 mock，落库不升级为 live。

## 建议输出契约（供讨论，不作为已存在类型）

建议由 D 在 `src/contracts/index.ts` 的 Provider 输出中新增下列可选字段，复用公共 Source；已有 Provider/Match 消费者可继续解析。最终命名与接口由 D 冻结后 B 再引用，B 不在私有目录复制 DTO。

| 字段 | 类型、必填性与语义 |
| --- | --- |
| `source` | 可选 Source，描述服务方基础资料；缺省表示未知，不解释成 live。 |
| `availability` | 可选对象或 null；缺省/null 均未知。有值时以下内部字段均必填。 |
| `availability.windows` | `{ startDate: YYYY-MM-DD, endDate: YYYY-MM-DD }[]`，真实公历、首尾包含、start ≤ end；按 Asia/Shanghai 的自然日解释，规范排序且不重叠。空数组只表示已确认在下述查询区间无可用窗口。 |
| `availability.coverageStartDate` / `coverageEndDate` | YYYY-MM-DD，首尾包含，起止合法；所有窗口在此区间内。防止把有限查询中的空数组解释成永久无档期。 |
| `availability.updatedAt` / `validUntil` | ISO 8601 时间，更新时间 ≤ 有效截止；到期不参与档期排序，显示“档期待更新”。未来更新时间或坏日期视为非法输出。 |
| `availability.source` | Source；固定样例为 mock，真实维护与验证的记录才能 live。 |
| `performance` | 可选对象或 null；缺省/null 表示没有可靠汇总。有值时以下字段均必填。 |
| `performance.basis` | 首版建议固定 `completed_order_review_average`，明确算法口径，不暗示准时率。 |
| `performance.averageRating` | 1–5 的有限数或 null，建议均分四舍五入到两位小数；无样本时只能 null，不能为 0 或默认满分。 |
| `performance.reviewCount` | 非负安全整数；0 与均分 null 成对，正数与非空均分成对。每份已完成接单最多计一次。 |
| `performance.calculatedAt` | ISO 8601 服务端计算时间，非未来；建议按读取时一致快照计算。若采用缓存，D 须另冻结有效期，不能无限使用旧缓存。 |
| `performance.source` | Source；均分与样本数属于同一来源口径，不把 mock 样本掺入 live 汇总。 |

建议继续通过 `GET /api/provider` 返回 Provider[]，基础字段保持兼容。B 的浏览器与 `/api/match` 数据入口都需要同一批来源可追溯的候选。请 D 提供可复用的服务端只读适配器或明确读取方式，避免浏览器用新数据而匹配 API 仍用固定数组。混合/未知来源整体保守标 mock，逐条/逐维度保留来源；全 live 才允许整体 live。合法空样本与查询失败必须区分，存储或输出错误返回失败信封，不伪装成 null/空成功，不回退固定样例。

响应示例（仅展示拟新增部分，**合成 mock 示例，并非现有 API 响应或真实档期**）：

```json
{
  "source": "mock",
  "availability": {
    "coverageStartDate": "2026-11-15",
    "coverageEndDate": "2026-12-31",
    "windows": [{ "startDate": "2026-11-20", "endDate": "2026-12-10" }],
    "updatedAt": "2026-11-14T00:00:00Z",
    "validUntil": "2026-11-15T00:00:00Z",
    "source": "mock"
  },
  "performance": {
    "basis": "completed_order_review_average",
    "averageRating": 4.5,
    "reviewCount": 2,

  }

```

旧资料可不含新增字段；新适配器未知时建议显式 null；已成功查询且无评价时输出 averageRating=null、reviewCount=0。不得回填伪造日期、评价或来源。历史缺少 orderId 的评价不能自动补成有效样本；发现关联坏数据须按 D 冻结的失败规则处理，不能悄悄舍弃后声称完整统计。

## B 后续排序与展示边界

`Demand.desiredDays` 是期望施工时长，目前没有期望开工日或最晚完工日。第一版只能提示“有效窗口是否可容纳 N 个连续自然日”，显示具体窗口与来源；不能声称满足业主截止日或保证工期。不从描述文本推断日期，不由 B 修改 A 的需求表单。若要精确日期匹配，另请 D/A 冻结需求日期输入及业务定义。

城市和施工工种继续是硬过滤；档期/评价未知不作为淘汰条件，null 不当作零分。建议先让新增指标只用于基础同分候选的细分排序，并展示理由与样本数；指标是否启用必须在整组候选上采用一致规则，不能在每次两两比较时临时跳过缺失值，避免排序不传递。推荐同分组只有在同一口径、来源一致且该维度数据全有效时启用该维度，否则保持稳定 ID 次序并提示资料不足；最终优先级与样本门槛由 D/B 在字段冻结后确认。mock 与 live 不当作同等真实历史混合排名。
