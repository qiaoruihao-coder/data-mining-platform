# D：登录限流仅统计失败，不因单人请求封锁所有业主

日期：2026-11-14，基于 main `6b0561b`，修正 #90 的实际使用反馈。

## 先行变更

- 移除全局 5 分钟 60 次的持久锁定；一个账号的失败不影响其他账号。
- 每个规范化登录名只统计认证失败（401），15 分钟最多 5 次；第六次起返回 429 和剩余窗口 Retry-After。成功登录不计数，并在签发会话的同一事务中清除该账号失败记录。未知账号采用同样规则与密码计算，失败计数不保存原始登录名或密码。
- 400、403、503、密码计算繁忙及已经限流的 429 均不增加失败计数。保留进程最多两个并发密码计算的短暂容量保护（Retry-After: 1），不把它变为全站 5 分钟锁定。
- 数据库计数使用 `failure:` 前缀的新键，忽略旧版可能包含成功次数的账号键和 global 键，避免升级后继承错误锁定；过期计数随失败写入清理。无需 schema 迁移或新依赖。
- 验证密码前检查失败窗口；签发事务再次检查窗口及当前凭证/角色，避免密码计算期间新增的失败被旧请求清除。失败计数的读取/递增在 Serializable 事务内，签发失败不会清空已有失败历史。存储错误仍返回中性 503。

## 验收

实际 SQLite/密码测试：连续成功超过 5 次不锁定；失败后成功清零；5 次失败后限流且重连保留；未知账号同样限流；一个账号失败不影响另一账号；旧版 global=60 和成功计数不造成锁定；到期恢复；并发失败不丢计数；验证期间触及上限不能签发；签发存储故障保留失败计数。

接口和 cookie 不变，不修改客户端、账号密码或现有业务数据。

## 实际结果

`npm run check` 512/512、`npm run build`、`npm run scope -- --role D --base origin/main`（5 个文件）与 diff 检查通过。新增回归覆盖连续 6 次成功、真实错误密码/未知账号限流、其他账号不受影响、旧版计数兼容、并发失败计数、验证期间限流及签发失败保留失败历史。无新增 mock；测试只使用隔离 SQLite 的合成账号。
